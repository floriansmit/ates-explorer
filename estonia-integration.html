Estonia integration · request for EGT

Proposed provider-neutral contract, not an existing EGT endpoint or confirmed EGT schema.

Preferred: a documented HTTPS point-query API accepting easting/northing in L-EST97 (EPSG:3301), with optional WGS84 support. Return all intersected units from shallow to deep in JSON. Request and response must identify CRS and axis order explicitly. No specific endpoint URL is assumed.

Minimum useful response

  • Stable unit ID/name and aquifer/aquitard/other role.
  • Numeric top and base elevations, their units, vertical datum and sign convention. Depths are also acceptable with a ground/reference elevation and explicit conversion.
  • Model ID/version, coverage status, resolution and source/provenance. No-data or outside-coverage responses must be explicit.
  • Kh where available, with units and whether measured, assigned or calibrated. Missing conductivity should be null, never zero. Geometry alone is enough for a first connection.
  • Licence permitting reuse/display and derived calculations; authentication/rate limits; CORS for direct browser use or permission to access through a server adapter.

Valuable optional data

Kv, groundwater heads by aquifer and scenario/date, effective porosity, storage properties, ambient groundwater temperature, salinity, hydraulic/thermal-property uncertainty and evidence, faults and model confidence. Head surfaces allow us to derive gradients after confirming support and scenario; we must distinguish Darcy flux from pore velocity.

If no API exists

GeoTIFF (ideally Cloud Optimized GeoTIFF) or ESRI ASCII grids for unit top/base and properties; documented NetCDF; or GeoPackage / database tables for boreholes and attributes. Provide CRS, vertical datum, unit catalogue, units, nodata values, extent, model version and reuse terms. Structured or unstructured MODFLOW/FEFLOW model files are also usable with their geometry, properties and metadata, but require preprocessing into a profile-query service. Surface meshes (GOCAD TSurf / VTK etc.) require unit identities, geological relationships and datum; they need more preprocessing than rasters. A texture-only 3D viewer is insufficient.

WCS or a numerical REST service is particularly convenient for rasters. WFS/OGC API Features can supply boreholes/attribute features, but do not automatically provide 3D surfaces. WMS is primarily for viewing; use GetFeatureInfo only if actual numeric layer elevations are exposed reliably.

Questions for EGT

Which current model should be used for a Tallinn site? Is it the national model, a local/regional model or a Baltic Artesian Basin derivative? Can both saturated geometry and hydraulic properties be supplied? Is there an existing numerical point-query service, downloadable grid package, or an internal service that could be made available?
